# 90-dagen MVP-plan — Belgium Accounting AI Layer

_Datum: 2026-06-07_

## Doel
Binnen 90 dagen een geloofwaardige MVP neerzetten voor een **AI control / review / close layer** bovenop bestaande boekhoudplatforms, klaar voor een eerste Belgische design-partner pilot.

De MVP moet bewijzen dat we:
- documenten en e-mails kunnen structureren
- ontbrekende stukken automatisch kunnen signaleren
- review findings kunnen genereren
- close-status zichtbaar kunnen maken
- AI-samenvattingen kunnen leveren met audit trail

**Niet het doel:** een nieuw boekhoudpakket bouwen.

---

## Scope lock

### In scope
- 1 boekhoudbron
- 1 mailboxbron
- 1 documentbron
- 1 pilotteam
- 30–50 dossiers
- document intake
- e-mailtriage
- ontbrekende-stukken workflow
- basis review/control engine
- close cockpit v1
- reviewer summary
- audit trail

### Out of scope
- multi-ERP vanaf dag 1
- autonome boekingen
- fiscale filing automation
- betalingen
- brede klantchatbot
- complexe write-back
- volledige rapportering suite

---

## MVP-architectuur in één blok

```text
Accounting connector → canonical store → controls engine → reviewer workbench
Email/document ingest → extraction/classification → request workflow → close cockpit
LLM layer → summaries / concept messages / explanations
Governance layer → approvals / logs / tenant security / evidence trail
```

## Doel
Fundament neerzetten. Geen glamour, wel ruggengraat.

### Deliverables
1. projectstructuur en repo-/werkmapdiscipline
2. scope lock document
3. canoniek datamodel v1
4. event- en entitymodel voor dossiers, documenten, requests en findings
5. keuze van eerste boekhoudbron
6. keuze van eerste mailboxbron
7. keuze van eerste documentbron
8. pilotflow op whiteboardniveau uitgewerkt
9. audit-eventmodel v1
10. eerste klikbare reviewer/close-wireframes

### Producttaken
- definieer kernentiteiten:
  - client
  - dossier
  - reporting period
  - document
  - request
  - finding
  - close status
  - AI recommendation
- bepaal minimale fields per entiteit
- leg severity-, confidence- en status-taxonomie vast
- definieer lifecycle van een request
- definieer lifecycle van een review finding

### Integratietaken
- selecteer 1 accounting source voor v1
- definieer ingest-contract voor GL, open items, btw-info en documentlinks
- definieer ingest-contract voor mailbox en attachments
- definieer ingest-contract voor document store
- ontwerp delta sync model

### AI-taken
- definieer documentclassificatie-outputschema
- definieer summary-outputschema
- definieer concept klantmail-outputschema
- definieer explanation-outputschema voor findings

### Governance-taken
- definieer tenant boundary
- definieer user roles:
  - dossierbeheerder
  - reviewer
  - manager
  - partner
  - admin
- definieer approval gates
- definieer logstructuur voor AI-aanbevelingen

### GTM-taken
- finaliseer ICP
- maak shortlist van design-partnerkenmerken
- schrijf discovery script voor pilotgesprekken
- definieer pilot-KPI-baseline

### Exit criteria dag 30
- scope is locked
- datamodel staat
- eerste integratiespecs staan
- wireframes bestaan
- governance basis staat
- design-partner profiel is scherp

## Fase 2 — Dagen 31–60

## Doel
Eerste werkende intelligence- en workflowlaag neerzetten.

### Deliverables
1. document ingest v1
2. e-mail ingest v1
3. basis classificatiepipeline
4. dossiermatching v1
5. request workflow v1
6. findings engine v1
7. reviewer workbench v1
8. close cockpit v1
9. audit logging werkend

### Producttaken
- bouw document intake flow
- bouw attachment parsing flow
- bouw dossier- en periodekoppeling
- bouw request states:
  - open
  - waiting on client
  - received
  - needs review
  - resolved
- bouw findings states:
  - new
  - acknowledged
  - in review
  - resolved
  - dismissed

### Controls v1
Implementeer alleen de meest waardevolle checks:
- ontbrekend document
- boeking zonder documentlink
- afwijkend rekeninggebruik versus historiek
- inconsistent BTW-tarief
- duplicate invoice signal
- basic bank/open-item mismatch signal

### AI-functionaliteit v1
- documentclassificatie
- korte dossier summary
- concept klantmail voor ontbrekende stukken
- explanation block per finding

### UX v1
Reviewer workbench toont:
- dossierstatus
- open findings
- missing documents
- open requests
- AI-samenvatting

Close cockpit toont:
- dossiers per status
- blockers
- dossiers met meeste uitzonderingen
- nearing deadline signalen

### Governance
- elke AI-output krijgt timestamp, model, inputscope en bronverwijzing
- manual approval voor externe mails en materiële reviewacties

### Exit criteria dag 60
- end-to-end interne demo werkt
- minimaal 1 documentflow werkt van intake tot finding
- minimaal 1 requestflow werkt van missing doc tot resolved state
- cockpit toont echte statusentiteiten
- AI-output is gelogd en verklaarbaar

## Grootste risico’s in de eerste 90 dagen

### Risico 1 — scope creep
Mitigatie:
- geen extra ERP-dromen toelaten
- 1 bron per type
- 1 pilotteam

### Risico 2 — integratievertraging
Mitigatie:
- read-mostly architectuur
- file/API fallback toestaan
- geen diepe write-back blokkade in MVP

### Risico 3 — AI lijkt slim maar is operationeel zwak
Mitigatie:
- hard workflow-first ontwerpen
- structured outputs
- confidence + review queues

### Risico 4 — demo zonder echte waarde
Mitigatie:
- altijd focussen op missing docs, reviewfrictie en close blockers
- geen generieke chatbot-demo als hoofdshow

### Risico 5 — governance wordt te laat toegevoegd
Mitigatie:
- audit trail vanaf dag 1
- approvals vanaf eerste flow
- bronverwijzingen verplicht
